# Stage 1 (GRAPE / SE-detection) — Multi-GPU Feasibility Analysis

**Scope:** every file in `src/moe_compress/stage1/plugins/*.py` + `orchestrator.py` + `artifacts.py`, read in full.
**Hard constraint (from the user):** any multi-GPU scheme MUST preserve the per-GPU VRAM-aware auto-batch sizing — each replica/device probes ITS OWN free VRAM and sizes its own max batch. The existing resolver (`utils/auto_batch.py`) is per-device by construction (`CudaMemProbe(device)`), so the requirement reduces to: **spawn replicas with `CUDA_VISIBLE_DEVICES` pinned, and let each replica call the resolver locally** — exactly the Stage-3 cov template (`stage3/plugins/covariance_collection.py:1073-1209` `_cov_replica_worker` / `run_dp_covariance_collection`).
**Fidelity bar:** result-preserving — byte-identical for batch-INVARIANT stats (max/percentile/argmax); bounded ~1e-6 for reduction-accumulating sums under the per-sequence reduction pin.

> **Ablation-value caveat:** Stage 1 (GRAPE) is **SKIPPED** in by-the-book REAP/REAM ablations (uniform budgets + empty blacklist; the `_shared/` artifacts are stubbed via `gen_shared.py`). So multi-GPU Stage 1 only pays off for **GRAPE/SC-style full runs** that actually run the plugin chain. For the current REAP/REAM @ net-35% campaign it is **zero value**. Analyzed fully below regardless.

---

## How Stage 1 actually spends wall-clock time (orchestrator.py)

There are exactly **three GPU forward-pass concerns** and a long tail of CPU post-processing:

1. **Phase A — `ma_detection.run`** (orchestrator STEP 3): its OWN dedicated early-exit forward pass over the calibration set (default `phase_a_batch_size=32`), hooking every decoder layer + every MoE block. Tracks max-magnitudes + a first-layer Q99 buffer. Already auto-batched (`BATCH_INVARIANT`).
2. **Phase B — the ONE shared calibration pass** (orchestrator STEP 6, `run_calibration_pass`, default `phase_b_batch_size=16`): a single forward over ~1024 samples that simultaneously feeds **three** accumulators consumed by **five** detector plugins —
   - `downproj_max` (`DownProjMaxAccumulator`) → read by `three_way_and`, `aimer`, `magnitude_topk`, and (indirectly) `ablation_filter`'s ranking;
   - `output_reservoir` (`ExpertOutputAccumulator`, cap 256 tok/expert) → read by `cka_distance`;
   - `sink_routing` (`SinkTokenRoutingAccumulator`) → read by `sink_token`.
3. **Phase D — `ablation_filter.run`** (orchestrator STEP 9): `|candidates|` separate corpus-NLL forward passes (baseline + one per candidate, each zeroing one expert's `down_proj`). At ~60-100 candidates × ~13 batches each, **this is the Stage-1 runtime bottleneck** (the module docstring itself estimates ~15-30 min).

Everything after that — `three_way_and`, `aimer` (weight-only score), `sink_token`, `magnitude_topk`, `cka_distance` (small GPU bmm per layer, ~1s/layer), `damage_curve_dp`, `grape_merge`, `rco_budget` — is either tiny-GPU or CPU/NumPy post-processing on already-collected statistics.

**The single most important structural fact:** Phase A and Phase B are two *independent* data-parallel-able forward passes over the SAME calibration corpus, and Phase D is `|candidates|` independent forward passes. All three are the multi-GPU targets; the 11 post-processing plugins are NOT.

## The Phase-B shared pass — the central multi-GPU target

Phase B is **one** data-parallel forward that simultaneously populates three accumulators. A single DP pass (shard the 1024 calibration samples across N GPUs, replica-local auto-batch, reduce per accumulator) parallelizes the work for **five** detector plugins at once. This is the cross-plugin coordination win: do NOT build three separate DP passes — build ONE, exactly mirroring `run_dp_covariance_collection` which already reduces `B_acc` + `C_acc` from a single replica forward.

Per-accumulator DP-reduce contract:

- **`DownProjMaxAccumulator`** (`activation_hooks.py:639`): state is `per_expert_max: dict[(l,e)->float]`, updated by `val > current` (`:680`). **Max-reduce, batch- and shard-invariant ⇒ byte-identical** under DP (element-wise max of replica-partial dicts). Trivially safe — this is the `BATCH_INVARIANT` class.
- **`SinkTokenRoutingAccumulator`** (row 4): state is **sums** + integer counts, finalized to ratios. **Reduction-ACCUMULATING.** DP-correct under the per-sequence reduction pin: each replica sums over its disjoint shard; the parent sums the raw aggregate tensors key-wise, THEN finalizes. fp-sum reassociation gives ~1e-6 drift, ~1000× below the score-ratio (10.0) / freq (0.99) decision thresholds ⇒ identical candidate set. **Reduce raw sums, not finalized ratios.**
- **`ExpertOutputAccumulator`** (`activation_hooks.py:695`): **reservoir sampling with `torch.rand`/`torch.randint`** (`:790-810`). This is **NOT byte-deterministic across a re-sharding** — the accepted-token set depends on the per-batch RNG stream and the order tokens arrive, which a shard partition changes. Two consequences:
  1. A DP reduce of reservoirs is **statistically equivalent** (still a uniform sample, cap 256/expert) but **NOT byte-identical** to single-GPU; and since CKA → GRAPE → budgets are deterministic functions of the reservoir, the final per-layer budgets can shift by a merge or two.
  2. Therefore the CKA reservoir is the **one fidelity hazard** in a Phase-B DP. **Recommended:** for the reservoir signal, prefer the **cache** path (`output_reservoir_cache`, row 12) — capture the reservoir once during the vLLM calibration run and hydrate it — rather than DP-reducing a randomized reservoir. If DP is used, classify the budget output as "statistically-equivalent, not byte-identical" and pin a tolerance test, not a golden-byte test.

**Auto-batch gap (factual, not a recommendation to change):** Phase B today is NOT wired to `resolve_batch` (only Phase A `ma_detection` and Phase D `ablation_filter` are). It runs at the fixed `phase_b_batch_size`. So a Phase-B DP would inherit "fixed batch per replica" unless Phase B is first given an auto-batch path. The user's hard requirement (replica-local sizing) is satisfied either way: with fixed batch each replica simply uses the fixed batch on its own device; if/when Phase B gets an auto path, the resolver is per-device by construction (`CudaMemProbe(device)`), so the spawn-with-pin template carries the property for free. **No change to `auto_batch.py` is needed for any Stage-1 DP scheme** — `size_candidate`/`run_with_oom_backoff` are already device-scoped; the multi-GPU layer is purely the spawn+shard+reduce wrapper.

## Stage-1 summary

**Runtime bottleneck ranking:**
1. **Phase D (`ablation_filter`)** — `|candidates|`+1 full holdout forwards. The dominant cost. → **TASK-parallel over the candidate list** (each GPU: model + fixed holdout slice, recompute baseline, process its candidate slice, union ΔNLL dicts; threshold once). Best paired with the existing **pinned-NLL** path for a clean batch-invariant guarantee. **Highest-value conversion.**
2. **Phase B (the shared calibration pass)** — one forward feeding 3 accumulators / 5 plugins. → **ONE data-parallel pass** (shard 1024 samples, replica-local auto-batch, reduce: max-merge `downproj_max` byte-exact, sum-merge `sink_routing` ~1e-6, reservoir-merge `output_reservoir` statistically-equivalent-only). Second-highest value; the cleanest because a single DP pass covers five plugins.
3. **Phase A (`ma_detection`)** — one dedicated forward. → **DP** (max-merge byte-exact + gathered exact Q99). Already auto-batched; the DP wrapper is the only new code. Also relieves the ~34 GiB Q99 host-RAM peak by sharding it.

**The 11 post-processing plugins** (`three_way_and`, `aimer`, `sink_token.run`, `magnitude_topk`, `cka_distance`, `damage_curve_dp`, `grape_merge`, `rco_budget`, `_floor`, + the 4 cache providers) are **CPU/tiny/sequential** — none is a multi-GPU target. `cka_distance` is the only one with a real GPU matmul, but it is ~1s/layer and only worth TASK-sharding if Phase D is already parallel and CKA becomes the relative tail (NWI otherwise). `grape_merge` and `rco_budget` are inherently sequential solvers.

**Cross-plugin coordination — the key insight:** Phases A, B, and D are the only forward-pass concerns, and **all three are independent forwards over the same calibration corpus**. The biggest structural win is recognizing that **Phase B is a single shared forward feeding five plugins**, so it should be ONE data-parallel pass (the `run_dp_covariance_collection` template applies directly: spawn N replicas, `CUDA_VISIBLE_DEVICES`-pinned, disjoint shards, per-accumulator key-wise reduce). Phase A can share the same shard-and-reduce machinery (different hooks). Phase D parallelizes orthogonally by candidate, not by data shard.

**Auto-batch preservation (the user's hard constraint) is satisfied with zero changes to `auto_batch.py`** for every scheme above: the resolver is already device-scoped (`CudaMemProbe(device)`, `size_candidate` uses `mem.total()` of the pinned device), and the Stage-3 cov template proves the pattern — each replica pins itself, then calls `resolve_batch`/`size_batch`/`run_with_oom_backoff` locally, probing its OWN free VRAM and sizing its OWN max batch. The per-sequence reduction pin (disjoint shards + reduce raw sums/maxes, not finalized ratios) makes the DP reduce batch-/replica-independent, so no cross-replica batch agreement is required.

**The one fidelity hazard:** the CKA `ExpertOutputAccumulator` uses randomized reservoir sampling, so a Phase-B DP reduce of it is statistically-equivalent but NOT byte-identical (and propagates non-deterministically into GRAPE budgets). Mitigate by sourcing the reservoir from the `output_reservoir_cache` sidecar instead of DP-reducing it, OR accept a tolerance-test bar for the budget golden on DP runs.

**Net recommendation for value:** if Stage 1 is ever the target (i.e. a GRAPE/SC full run, NOT a by-the-book REAP/REAM ablation where Stage 1 is skipped entirely), do **Phase D candidate-TASK-parallel first** (biggest bottleneck, cleanest fidelity via the pinned path), then **Phase B + Phase A as one shared DP shard/reduce** (max-exact + sink-sum-exact; cache the reservoir to dodge the RNG hazard).
